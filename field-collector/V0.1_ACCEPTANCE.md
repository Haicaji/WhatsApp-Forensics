# Field Collector v0.1 验收记录

记录日期：2026-08-08  
适用范围：Windows x86_64、被动 T0 纵向切片、非正式开发制品

本文只记录可由当前源码、测试或制品直接证明的事实。未完成项目保持为“未验收”，不得由
单元测试、合成 fixture 或成功构建间接替代。

## 1. v0.1 交付边界

v0.1 已实现一个与 Analysis Workstation 完全分离的便携现场采集产品：

- 原生 Rust 单机程序，不依赖 Node、Electron、Python、模型或案件数据库；
- 启动时只从自身 EXE 相对目录加载 Workstation 签名的勘察员配置与任务；
- GUI 无默认端口，自动从操作系统现有监听表筛选当前会话、已安装 Chrome/Edge 所拥有的回环
  候选，再以严格 CDP 握手确认；不扫描端口，技术回退参数只放在折叠诊断区；
- 只接受精确 `https://web.whatsapp.com` page target；
- 使用编译时固定 IIFE 执行 accounts、contacts、chats、messages 被动 T0；
- 流式生成版本化 WA Evidence Bag，并由独立 Rust verifier 验证后才晋升正式目录名；
- 同一便携 EXE 提供五步原生 GUI 和支持 CLI；GUI 只让现场人员选任务、输入一次口令、确认
  授权、选页面和开始采集，不在 AppData 持久化身份、表单或口令；
- 输出固定为 `evidence/staging` 与 `evidence/sealed`，handoff 固定写入 `handoff/`，不接受
  现场输入的输出目录、密钥路径、身份、机构、授权引用、时区或可信指纹；
- 生产二进制不包含发消息、创建群组、任意 JavaScript、历史同步、媒体下载或页面写入能力；
- 两账号写测试只能通过不随 Collector 发布的受控测试工具或浏览器连接器实施，并严格锁定
  `{A, B}`；该能力不得进入 Collector 生产二进制。

主动 T1、历史、媒体字节、Status、通话、频道、社区和断点恢复不属于本次完成声明。

## 3. 真实 Chrome 集成证据

已在 Chrome 151 上完成以下非证据内容集成检查：

- 修复 Chrome 对 `/json/version`、`/json/list` 的 keep-alive `Content-Length` 响应处理；
- 成功发现并严格选择真实 WhatsApp page target；
- 初始 target lock 正确区分主框架默认 Main World 与扩展 isolated world；
- 固定 IIFE 能在真实 WhatsApp Web build 上返回 allowlist 能力诊断；
- 未登录的专用 Profile 返回 `account_reader_signature_mismatch`，且明确
  `readyForPassiveT0=false`、`collectionStarted=false`、`evidenceBagCreated=false`；
- 上述诊断未创建 staging、未解锁签名密钥、未读取或输出账号标识。

这些检查只能证明协议与失败关闭行为，不证明真实聊天数据采集已经完成。

另已通过受控 Chrome 会话让两个现有测试账号各发送一条固定的私聊合成消息，并创建一个成员
集合恰好为 `{A, B}` 的合成测试群组，由 A、B 各发送一条固定群聊消息；未处理附件，也未涉及
第三账号。该操作只准备后续测试矩阵，不是 Collector 的采集证据，也不替代真实 T0。

## 4. 当前便携开发制品

制品：`out/whatsapp-field-collector-v0.1.0-windows-x86_64.zip`

- `publishable=false`：工作树尚未提交且 HEAD 无精确发行 tag，这是预期门禁结果。
- 已在便携配置/任务下发改造和全部回归测试之后重新构建；脚本自动定位 Visual Studio x64
  校验工具，并完成静态 CRT、文件白名单、SBOM、许可证、来源清单和可复现 ZIP 检查。
- ZIP 严格只含两个 EXE、许可证/SBOM/来源与发行清单，不含测试密钥、测试任务、`config/`
  或 `assignments/`。它是原始软件发行物，仍须由 Analysis Workstation 组装为签名的现场 U 盘，
  不能单独视为可出现场介质。

具体 ZIP、release manifest 与 source tree SHA-256 必须从同次构建输出和包内
`release-manifest.json` 读取，不在本文件中硬编码，避免验收文档参与来源摘要后形成循环引用。
该 ZIP 不是正式发布物；源码变化后既有摘要自动失效，必须重新运行便携发行脚本。

## 5. 尚未验收的硬门槛

以下任一项不得用“测试通过”或“真实页面能探测”替代：

1. 两个授权测试账号分别完成一次真实、只读 T0，生成两个独立 source/Evidence Bag；
2. 两个真实包均由随包独立 `waeb-verify.exe` 验证，且只报告非敏感计数与完整性摘要；
3. 在未安装 Node、Python、Rust、Visual Studio 和 VC++ Redistributable 的干净 Windows VM
   中，用 Workstation 生成的完整 U 盘目录以普通用户启动并完成采集/验证；
4. 目标 `10 万消息 + 10 GB 媒体、RSS < 512 MiB` 尚未进入 v0.1 被动 T0 的实测范围；
5. 原生便携 GUI 已实现并通过本机窗口启动 smoke test，但尚未在上述干净 VM 中完成整套真实
   采集、异常退出与中文字体回退验收；
6. clean、精确 tag、重新构建、双次可复现摘要一致之后，才允许标记 `publishable=true`。
7. U 盘盘符变化、空间不足、只读介质、任务过期、A 密钥执行 B 任务、配置/任务/私钥单字节
   篡改和 reparse 路径的整套 GUI 迁移验收仍需在真实移动介质完成。
8. Workstation 侧的 provisioning API、独立加密签名密钥库、CLI、勘察员公钥/任务登记和 U 盘
   端到端验证已实现；正式 Electron 可视化界面仍未完成，不得要求现场人员用开发命令代替。
9. 当前便携信任链可拒绝局部/逐字节篡改和未知口令的整包替换；若验收威胁模型包含“知道
   operator 口令并能用自定义工具重打包整盘的恶意勘察员”，还需引入不随盘交付的组织根
   证书或硬件密钥。实验室端无论如何都必须按本地任务登记表和勘察员公钥再次核验。

## 6. 双账号写测试约束

生产 Collector 永远保持只读。若为了构造测试矩阵使用两个授权账号执行发消息、反应、编辑、
撤回或建群，必须满足：

- 操作工具不链接、不打包进 Field Collector；
- 启动后先读取并锁定 Account A 与 Account B，本地参数只接受 `A`/`B`，不接受任意 JID；
- A 的唯一收件人是 B，B 的唯一收件人是 A；
- 新群参与者集合必须恰好为 `{A, B}`，发现第三账号立即终止；
- 只操作本次 run 创建的消息和群组 ID，不修改已有聊天或已有群；
- 测试内容固定为合成数据并带 run marker，不读取、转发或快照真实聊天正文；
- 两个账号仍分别采集为两个 Evidence Bag，工作站阶段再归入同一案件。
