# Field Collector v0.2 验收基线

## 产品边界

Field Collector v0.2 是从取证 U 盘运行的现场采集产品，不是 Analysis Workstation 的精简版。它只完成：读取 Workstation 下发的签名任务、引导勘察员使用现场计算机原有 Chrome/Edge Profile 加载只读扩展、采集一个已确认的 WhatsApp Web 页面、生成并独立校验一个 Evidence Bag。

每个浏览器 Profile、每个当前登录账号分别采集并生成独立 Evidence Bag。多包归案、检索、Agent 分析和报告均由 Analysis Workstation 完成。

## v0.2 固定架构

```text
原有 Chrome / Edge Profile
  → 操作者在目标 WhatsApp 标签页点击 MV3 扩展
  → 一次性配对的 127.0.0.1 WebSocket
  → 固定 extension relay / bridge 协议
  → 带版本与 SHA-256 的 MAIN World Adapter v2
  → Rust Collector 流式规范化、CAS、日志、完整性分级与签名
  → 独立 waeb-verify 校验
  → evidence/sealed/
```

- 扩展只拥有当前标签页的临时 `activeTab` 与 `debugger` 权限。
- 扩展只能连接固定回环地址，只接受固定 CDP 方法、固定函数和固定 Adapter 字节。
- Adapter 不提供发送、撤回、编辑、建群、加人、发布 Status/频道/社群、标记已读或 DOM 点击接口。
- 不使用 F12，不要求操作者填写端口、输出路径、密钥路径或案件元数据。
- 扩展外壳与 `wafc-extension-relay/1` 保持稳定；异步媒体任务使用 `wafc-bridge/2`，WhatsApp 私有模块适配集中在版本化 Adapter v2。

## 签名采集模式

Workstation 可签发两种模式：

- `passive_t0`：只读取当前已驻留 Store 数据，不请求历史或媒体。
- `comprehensive_readonly_v02`：先记录基线，再调用只读 Store loader 补全可观察历史，并请求可观察媒体 Blob。它可能引起网络同步和浏览器缓存变化，但不执行 UI 点击或消息写操作。

新建任务默认使用 `comprehensive_readonly_v02`；旧的 `passive_t0` 任务继续可执行。模式由签名任务决定，现场不可修改。

## 历史与媒体

- 历史补全只允许固定 `WAWebChatLoadMessages.loadEarlierMsgs` Store loader。
- 禁止自动打开会话、滚动、点击、聚焦输入框或使用 DOM fallback。
- 每个会话记录初始/最终消息数、轮次、返回数、新增数、空轮次、停滞轮次和终止原因。
- 采用有限轮次、单轮超时、连续稳定无增长终止；单会话失败不得伪装成成功。
- 页面端不得构造 ZIP，也不得一次性读取完整大媒体；Blob 按有限大小分片传给 Rust。
- Adapter 媒体下载必须作为后台 `MediaJob` 运行；`next()` 在等待期间快速返回 `progress`，不得
  等待完整下载 Promise。普通 CDP 调用约 10 秒；15 秒心跳连续两次未响应才判定本机通道断开。
- Rust 依据签名 `mediaPolicy` 独立执行缓存、网络尝试、重试、无进度/总时限、单文件/总量和
  磁盘余量限制；单媒体失败记录固定终态并继续队列，不得中止已取得的聊天和其他附件。
- Rust 计算实际 SHA-256/SHA-512、执行媒体魔数识别、写入无扩展 CAS 路径并生成媒体索引。
- media key、直接下载 URL、cookie、token、凭证和页面异常原文不得越过桥协议。
- 综合采集必须在结构化快照完成后、媒体分块边界和每个媒体终态保存两代加密认证检查点；检查点
  只能恢复已确认写盘的前缀，不能把页面声明当成已完成事实。
- 跨进程续采必须重新核对签名任务、Profile、浏览器/扩展/Adapter/WhatsApp build、当前页面
  来源、媒体计划与下一媒体边界。任一不一致均失败关闭，且不得追加审计、改写 staging 或更新
  检查点；核对通过后才记录 `acquisition_resumed` 并继续。

## 现场 GUI

现场主流程只保留：

1. 读取 U 盘签名配置并选择有效任务；
2. 选择 Chrome/Edge 与 Profile；
3. 点击“打开 WhatsApp”；
4. 按图文步骤加载 U 盘内扩展；
5. 在目标页面点击扩展并输入一次性配对码；
6. 核对当前页面并确认授权；
7. 输入一次密钥口令并开始；
8. 查看六阶段进度、阶段计数、附件序号/尝试/字节、实时耗时、最近更新时间、完整性摘要和校验结果；
   页面必须区分“正常工作”“等待返回”“耗时较长”和“已停止”，失败时保留最后一次已确认进度及普通语言处置步骤；
9. 必要时点击“安全取消采集”，在帧边界停止并保留未晋升 staging。

预检发现可恢复的综合采集时，GUI 必须以普通中文列出更新时间和“已完成附件/总附件”，默认提供
“继续上次采集”，并允许显式开始新采集。恢复核对期间显示独立进度阶段，不向现场人员暴露 CDP、
WebSocket、检查点文件名或页面内部标识。

配置、任务模式、操作者、机构、授权引用、密钥 ID、公钥指纹、输出位置、语言和时区均为自动或只读信息。

## 必须记录的状态影响

Evidence Bag 的采集日志和 `acquisition.json` 必须记录：

- 浏览器产品、版本、选定 Profile 的不可逆摘要；
- 浏览器产品在操作前是否运行，以及 Profile 精确占用状态不可验证的限制；
- Collector 请求打开浏览器的 UTC 时间；
- 扩展由操作者以 unpacked 方式加载及其版本；
- Adapter ID、版本、精确 SHA-256 和 WhatsApp build；
- `comprehensive_readonly_v02` 可能产生网络同步、缓存写入、媒体下载与浏览器日志痕迹；
- 只证明采集时段内该 Web 客户端可观察到的数据，账号级完整性与账号真实性不可验证。

系统不得使用“无痕”“账号全量”“已验证账号身份”等表述。

## 发布硬门槛

- `cargo test --workspace --locked`、全 workspace clippy `-D warnings`、Rust/Node 契约测试通过。
- Adapter 源码、注入 IIFE、扩展内副本与 manifest SHA-256 一致。
- 生产代码静态检查无 send/create/update/delete/revoke/markSeen、DOM 点击、任意脚本、任意网络或任意文件路径能力。
- mock E2E 覆盖 18 数据集、历史终止、媒体成功/缺失、ACK 重发、账号/标签页切换、恶意页面异常文本和中断 staging。
- 异步媒体测试覆盖延迟 Blob 期间 `next()` 持续快速响应、Rust 主导缓存未命中/重试/终止、
  单附件失败后继续、空间限制、取消以及心跳丢失；不得再依赖 45 秒通信超时。
- 恢复 E2E 必须覆盖“第一个媒体完成后断线→进程重启→同一来源继续→同一 evidence/source→无重复
  记录与媒体→独立校验通过”；错误来源必须在任何追加前失败，原审计与加密检查点逐字节不变。
- 使用授权测试账号在 Chrome 与 Edge 原 Profile 各完成至少一次真实只读采集；不发送任何消息，不修改现有聊天、群组、Status、频道或社群。
- 独立 verifier 验证真实包；任意 payload、媒体、日志、manifest 或签名单字节篡改均失败。
- 10 万消息/10 GB 媒体路径不构造全量内存 ZIP；媒体按块写盘。
- 开发制品标记 `publishable=false`；正式制品仍要求 clean tree、精确 tag 和干净 Windows VM 验收。
